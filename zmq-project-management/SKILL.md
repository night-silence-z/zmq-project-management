# 自适应项目治理

以“最小充分流程”为第一原则：只执行足以让项目可继续、可解释、可验证、可交接的管理动作。不存在关键决策、风险、阻塞、项目基线或正式状态变化时，不为留痕而留痕。

## 1. 先判断是否需要项目治理

满足任一条件时使用项目治理：

- 工作预计跨多个会话、多人或多个 AI。
- 存在多个相互依赖的产出物、权威定义或正式验收。
- 需要保留关键决策、风险、授权、版本关系或交接上下文。
- 项目已按本 skill 建档，需要继续推进。

一次性回答、孤立的小修改或无需后续接续的简单任务，默认直接完成，不创建项目目录、README 或台账。用户明确要求建档时除外。

## 2. 选择最小治理模式

依次判断：

1. 本次工作是否改变已确认的目标、范围、定义、约束、依赖、方法、验收标准或关键决策？
2. 本次工作是否跨越定稿、交付、发布、阶段验收、长期挂起、移交或结束等正式关口？

| 模式 | 进入条件 | 核心动作 |
| -- | -- | -- |
| 轻量日常迭代 | 两问都是否 | 读直接相关内容，完成工作，按风险验证；无关键事件则不更新管理文件 |
| 项目基线变化 | 第 1 问是、第 2 问否 | 更新一个权威源与一条关键决策；必要时更新当前状态 |
| 里程碑收口 | 第 2 问是 | 对照验收标准、核对状态与版本、形成正式证据和交接 |

- 默认使用轻量日常迭代，不因任务看起来复杂或验证较多而自动升级。
- 仅在升级会改变管理动作时简短说明升级原因；不要把内部清单复制给用户。
- 基线决策落定后，将后续执行降回轻量日常迭代；不要让一次基线变化把整轮工作持续升级成里程碑。

## 3. 将验证强度与治理模式分开

根据潜在影响选择常规验证或强化验证。满足任一条件时强化验证：

- 结果难以撤销、影响范围大或失败代价高。
- 涉及敏感信息、合规、资金、权限、他人权益或共享资产。
- 改动触及多个相互依赖的组件、材料或结论。
- 依赖尚未确认的外部能力、资质、数据、许可、预算或资源。

外部条件未确认时，先做最小可行性核验，再投入完整实现。验证强度可以提高，但不得因此自动生成里程碑文档、升级活文档版本或执行全项目收口。

## 4. 执行轻量日常迭代

### 开始

- 优先使用当前会话上下文和任务直接相关的文件。
- 新会话、换执行者或上下文不足时，只读取 README 的“当前状态”、相关权威源片段和直接关联的未决项；不要默认读取完整台账。
- 对版本库只查看必要的状态和少量近期提交；不要把全量历史或大段差异载入上下文。

### 进行

- 在既有基线内完成工作。
- 仅在出现关键决策、风险、阻塞、推翻、授权边界或需要跨会话接续的结果时落账。
- 不因普通进展更新 README、指针表、任务清单或权威源。

### 结束

- 执行与风险相称的验证。
- 仅当阶段、下一步、阻塞、当前冻结交付物或权威源指针确实变化时更新 README。
- 不默认运行项目健康检查，不生成独立验收文档，不升级活文档版本。

## 5. 处理项目基线变化

将以下内容视为项目基线：目标与受众、范围与优先级、事实与定义、方法与路线、外部依赖、关键约束、风险与授权边界、验收标准、已确认决策。

执行顺序：

1. 读取与变化直接相关的权威源和既有决策，不做全项目读档。
2. 若变化依赖外部条件，先核验可用性、资格、成本和限制。
3. 明确“原来是什么 → 改成什么 → 为什么 → 影响什么”。
4. 在唯一权威源原位更新定义；在台账只新增一条关键决策或推翻记录。
5. 仅同步真正受影响的材料；不要把同一定义复制到 README、计划和验收文档。
6. 决策完成后回到轻量日常迭代。

需要详细的基线、权威源与记录规则时，读取 [references/基线与记录.md](references/基线与记录.md)。

## 6. 执行里程碑收口

仅在正式关口执行完整收口：

- 对照启动卡或当前有效验收标准逐条核对。
- 明示未达标、缺证据和验证边界；需要改变已定稿内容时先请用户裁决。
- 核对冻结交付物、版本关系、当前状态、开放风险和授权事项。
- 按需运行 `scripts/health_check.py 项目根 --level milestone`。
- 权威术语发生变化且存在禁用词表时，运行 `scripts/check_terms.py`。
- 仅在正式交付、发布或确需长期保存证据时生成验收、交接或复盘材料。

完整步骤见 [references/里程碑与交接.md](references/里程碑与交接.md)。

## 7. 控制文档与版本成本

- 将 README、台账、执行清单、Backlog、权威定义文件视为活文档：原位维护，历史优先交给版本控制系统。
- 将正式报告、送审方案、定稿设计、发布包和用户明确要求冻结的材料视为冻结交付物：新增版本，不覆盖已冻结版本。
- 不按“能被阅读”判断是否升版；按“是否已冻结、是否独立验收、是否需要指名回退”判断。
- 仅为冻结交付物维护当前版指针；普通工作文件不进入产出物线。

详细规则见 [references/版本与产出.md](references/版本与产出.md)。

## 8. 保留交接能力

- README 只保存当前阶段、最近结果、下一步、阻塞、冻结交付物指针和权威源指针。
- 台账只保存关键决策、待确认、风险、阻塞、推翻和里程碑结果。
- 多人或多 AI 并行时，在关键事件中注明执行者；不要各建一套台账。
- 用户提出交接、项目长期挂起或更换执行者时，从 README、台账和版本状态现场生成交接摘要，不常驻维护重复文档。

## 9. 遵守授权边界

- 在用户授权范围内执行本地、可恢复、任务直接需要的操作。
- 对 push、部署、发布、外发、付费、同步协作平台、删除共享资产或其他触达他人的动作逐次确认；一次授权不延伸到下一次。
- 在修改已冻结交付物、重组存量项目或处理疑似当前版冲突前，先给出候选与推荐并等待裁决。

- 基线、权威源、台账或当前状态管理：读取 [references/基线与记录.md](references/基线与记录.md)。
- 冻结交付物、版本线或指针关系：读取 [references/版本与产出.md](references/版本与产出.md)。
- 阶段验收、交付、交接、挂起或收尾：读取 [references/里程碑与交接.md](references/里程碑与交接.md)。
- 需要跨领域正反例时：读取 [references/场景与反例.md](references/场景与反例.md)。
