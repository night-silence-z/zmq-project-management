# 持续迭代与需求

## 让迭代沉淀为当前有效逻辑

适用于 Demo、产品探索及其他通过反复反馈形成成果的工作。复用已有需求文件、Issue 或迭代记录；确实没有可承载的地方且需要跨会话持续记忆时，建立一份轻量“当前需求”。不要求每轮新增文档。

有实质逻辑变化时，在实现本次变化的同时更新对应条目。条目按场景/流程/规则组织，可按需要包含：

| 信息 | 用途 |
| -- | -- |
| 当前有效行为与适用条件 | 明确现在按什么逻辑执行，包括必要的异常与边界 |
| 来源/状态 | 用户提出、用户确认、AI 暂定；实现状态与用户验证状态分开 |
| 对应产物 | 页面、Demo、代码、图稿或文档链接，按实际可用粒度 |
| 待验证或未决问题 | 用户应体验什么，哪些分支尚未确认 |

不用为每个样式调整建立需求条目。用户明确修改细节就是该细节的指示，不需要再问是否允许记入当前需求；但没有表达的边界不能据此默认为已确认。

覆盖被替代的当前逻辑，避免把全部历史要求并列成仍然有效。历史优先交给版本控制或已有迭代记录；若没有历史能力，保留一条被替代说明或原文指针。重要推翻保留理由与影响，普通变化无需再复制一份台账。

## 保持轻量模式

同一目标下的页面、条件分支、字段与交互调整，通常仍是日常迭代，即使迭代了很多轮。判断基线变化看是否改变已确认的目标、范围边界、关键定义或承诺，不看更新了多少需求。

暂定交互、占位数据、模拟服务和 AI 自选方案要标注。能运行不证明业务正确，用户提出的逻辑也不等于已经通过真实场景验收。第一版或初步评审 Demo 不自动冻结；冻结和发布遵循用户明确意图。

## 从试用到下一轮

交付本轮结果时，说明变更和关键逻辑、AI 检查覆盖、模拟/未实现边界，以及最值得用户验证的场景与预期。反馈能定位到现有规则即可，不强求用户填写测试表。

根据用户反馈只更新相关需求及实现；若反馈与旧要求冲突，展示冲突和后果帮助决策。不把“还没试”写成“验收通过”，也不因等待用户试用阻塞其他已授权且独立的工作。

## 输出需求文档

用户表示可形成需求时，以“当前有效需求 + 确认过的决策 + 相关 Demo/图稿”作为主要输入。代码和界面可核对实现，不是自动生成产品意图的权威源。

将已确认逻辑、AI 暂定部分和缺失信息分开交给文档工作流；重要缺口集中提问，未阻塞部分可保留明确占位。不要在整理阶段悄悄补充产品逻辑、把试验方案写成已批准需求。

若环境有适用的需求文档 skill（例如 feishu-requirements-doc），按其能力边界完成结构和表达；没有则使用用户提供的格式，不安装依赖。仅排版请求不追加产品审查。草稿、真实文档写入和对外发送分别遵循用户本次或已有授权。
