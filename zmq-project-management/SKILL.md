# 自适应项目管理

帮助项目记住“为什么做、当前有效逻辑、做到哪里、什么尚未确认”，不把日常推进变成收口仪式。适用于研发、Demo 与需求、分析与报告及混合项目；具体产物由相应专业能力完成。

## 目标先对齐，流程再按影响选择

遇到模糊的新方向，先探索真实使用者、场景与问题，以及第一版要支持的判断。分轮追问，每轮只问少量影响方向的问题，后续问题承接用户回答；不要只收集文件名、页面清单就开始。核心场景与第一版用途清楚即可推进，细节可通过迭代发现。

目标探索不依赖建档，也不意味着必须建立完整基线。已有明确目标的局部任务直接执行；用户要求“先出一版”时简短说明暂定假设后开始。新方向、理解冲突或关键取舍才重新对齐。详见[启动与接管](references/启动与接管.md)。

| 模式 | 判断依据 | 最小管理动作 |
| -- | -- | -- |
| 轻量日常迭代（默认） | 既有方向内探索、实现、修正、整理、用户试用与普通接续 | 做任务；有有效需求变化就原位记录，状态确有变化才更新入口 |
| 项目基线变化 | 改变已确认的目标、边界、关键定义、承诺或验收依据 | 更新相关权威源，保留决策理由与受影响范围 |
| 里程碑收口 | 用户明确要求正式定稿、发布、阶段验收、冻结、正式移交或结束 | 围绕本次关口检查交付条件、证据、版本指针与未决事项 |

风险决定检查深度，不直接决定治理模式。任务多、改动多、耗时长、Demo 迭代次数多，都不是升级理由。“给我看看”“总结一下”“下次继续”也不自动成为正式交付。只在升级会增加动作时简短解释原因；发现影响超出当前模式再调整。

## 持续记忆，按变化读取和记录

- 先利用本会话已读且仍有效的信息。跨会话先读已有入口和当前任务直接相关的记录；缺失、冲突或依赖变化才扩读，不每轮重扫全部项目资料。
- 复用项目现有文档、Issue、任务系统或历史；没有连续性需要不建骨架，不强制改目录。模板和脚本只是可选起点。
- 需求细节可以持续更新而不升级基线。区分用户提出/确认的逻辑、AI 暂定的实现选择，以及实际验证结果；“已实现”不等于“用户认可”。
- 同一事实只维护一个当前权威源；入口保留指针，关键决策保留理由。无需把同一次更新复制进 README、台账、版本记录和需求文档。
- 活文档原位维护；只有需要保留独立交付快照时才建立冻结版本。不同报告是不同产出物，不是彼此的新版本。

## 验证到足够支持本次结论为止

按产物用途、变更依赖与风险选最小充分检查；尊重项目已有必需检查，不用管理流程额外复制一套。

- 代码检查受影响行为与相关依赖；Demo 重点验证改动的展示/交互，明确模拟边界，不自动套用生产级全回归。
- 需求文档检查与已确认逻辑的一致性、结构及关联材料；分析报告检查相关数据、计算、口径和证据，不对不受影响的报告全部重跑。
- 复用覆盖当前相关内容、输入和环境的有效证据。仅当新变化使证据失效、检查失败、有实质疑点或项目规则要求时补查；不要因进入总结、提交或交接阶段再跑同一检查。
- 达到本次检查目的即停止。说明没检查什么、为何留给用户；用户的业务与体验判断不能用 AI 自检代替。

## 在既有授权内继续，在关键变化处停下

沿用用户对同一目标、对象和范围已给出的授权，不因换轮次、工具或执行到发送步骤重复询问。明确要求发送给指定对象的内容即可执行相应发送；“完成任务”本身不包含额外通知或新增收件人。

新对象、范围外写入、敏感内容外发、显著费用、不可逆影响或关键方向不明时，先确认变化部分。运行环境的权限限制照常遵守；失败重试若结果不明，先查是否已生效，避免重复发送或提交。

## 交还用户可验证的结果

按本次实际工作简短说明：完成什么、关键逻辑、AI 已检查及边界、需要用户验证/决定什么。需要试用时给具体场景与预期，不只说“请测试”。没有新结果就不机械填四段；普通反馈无需生成验收文档或宣布里程碑结束。

## 可选工具

仅当它们适配当前项目且能回答具体问题时运行：

- [init_project.py](scripts/init_project.py)：创建新项目最小骨架；默认不写 AGENTS/CLAUDE，可显式选择。已有项目先只读盘点。
- [health_check.py](scripts/health_check.py)：检查指定入口中的本地冻结指针；支持自定义入口路径和显式目标文件。不证明业务正确、用户验收或外部链接可访问。
- [check_terms.py](scripts/check_terms.py)：在术语确实变化时，按权威源检查受影响文件，不作为每轮固定动作。
