# 启动与接管

## 先探索目标，不以建档为前提

用户只给一个方向时，帮助其表达脑中的业务场景，不立即把“做几个页面/报告”当成已明确的目标。优先识别：

- 谁在什么实际场景下做什么，现在如何处理、卡在哪里。
- 希望改变什么；第一版供谁体验、评审或决策。
- 有哪些会改变方向的边界、约束和未知，而非先追问所有功能细节。

从用户已给出的材料提取已知项，只问影响下一步的缺口。每轮通常一至三个问题；下一轮利用回答继续深入，不重复问已明确的信息，也不一次抛出完整问卷。抽象描述难以回答时，可以用一个具体使用场景或互斥选择帮助说明，并允许用户纠正这些例子。

开始制作前简短复述“我理解的场景/问题、第一版用途、暂定范围与未决假设”，留给用户纠偏。不是每个项目都要机械走完同样轮数：信息充分便开始；核心方向仍有歧义则继续问，而不是自信补全。若用户说“先做一版看看”，在可逆范围按明确标注的假设开始，关键风险仍单独处理。

进入执行的充分条件是：核心场景与问题可解释、第一版要验证的用途清楚、剩余未知可作为可逆假设处理。探索阶段不要求精确 KPI 或全部验收细节。

## 当前理解与已确认基线分开

把有跨会话价值的理解放在现有入口或需求记录中，标注“已确认 / 暂定 / 待探索”。用户认可第一版方向不等于冻结全部交互细节。后续按反馈逐步完善，不将启动卡全表自动冻结。

可参考[启动卡模板](../assets/templates/启动卡.md.tmpl)，只保留对项目有用的字段。真正改变已确认目标或重要承诺时才记录基线决策；明确局部修改不重新访谈。仅要求按既定内容排版文档时，不扩展为产品目标审查。

## 接管和恢复

1. 先用已有会话、README/索引、任务记录确认当前目标、最近结果和下一步；然后读取本任务涉及的具体材料。
2. 区分可复用事实、可能过时的证据和未知信息。只有冲突或关键缺口才补读历史、询问用户。
3. 复用目录、文件名与权威源，不为满足模板重组项目。涉及迁移、删除、覆盖或权限变化时确认具体范围。

接管已有项目不等于重新立项，也不默认重跑历史验证。

## 何时建档

需要跨会话推进且现有记录无法承载时，再建立最小入口与记录；一次性任务可以只用会话。目标探索与是否建档是两项独立判断。

新项目可使用：

```text
python scripts/init_project.py 项目名 --base 工作区
python scripts/init_project.py 项目名 --base 工作区 --type 分析 --bootstrap agents
```

默认只创建总览与台账；权威源、需求记录或多成果关系在实际需要时增加。仅在用户需要完整目录或明确自举规则时使用 --full 或 --bootstrap；不修改全局配置。空骨架不是立项完成的证据。
