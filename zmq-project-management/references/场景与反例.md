# 场景与反例

用影响而非关键词选模式；此表用于拿不准时，不是每轮检查清单。

| 场景 | 通常模式与处理 | 不应附加 |
| -- | -- | -- |
| 新方向只说“做个方便团队用的工具” | 先围绕使用者、真实场景与第一版用途分轮探索 | 先建完整骨架再问目标 |
| 用户清楚指定局部交互调整 | 轻量；改实现及对应当前需求 | 重问整个项目目标 |
| 连续迭代许多版 Demo | 轻量；保留当前有效逻辑及暂定边界 | 每版升级基线、冻结并出 PRD |
| 用户确认减少一个核心服务对象 | 基线；更新边界、原因和受影响成果 | 全量重跑无关测试 |
| 用户要求整理既有逻辑为 PRD | 按当前逻辑整理，标出未确认点 | 从代码补全业务规则 |
| 两份报告共用输入但方向不同 | 分开成果和方法，识别实际共用约定 | 强制统一分析方法 |
| 一份报告纠正措辞 | 轻量；检查相关事实和文字 | 重算所有报告 |
| 共享计算的公式错误 | 查受影响成果并针对性复算；若改变关键结论则更新基线 | 把高风险本身视为正式关口 |
| 已有效检查的同一内容进入总结 | 引用检查结果与边界 | 再跑一次相同检查 |
| 已要求将本次结果发给指定对象 | 授权内发送，结果不明先核实 | 因换工具再次索要同一授权 |
| 用户说“今天先到这，下次继续” | 轻量；留下必要恢复点 | 自动定稿、升版本、做验收包 |
| 用户要求正式发布当前成果 | 里程碑；检查该发布的条件与权限 | 将未确认的用户验收写成通过 |

复杂任务可包含不同局部动作；仅让确实受影响的部分升级，不将最高模式扩散到全项目。
