# 自适应项目管理

**默认直接做任务。** 目标、范围和当前做法已清楚的局部修改或试用，复用本轮已有信息，做必要检查即可。没有需求、决策、状态或成果入口变化，就不读额外管理参考、不写管理记录。具体成果由相应专业能力完成。

## 何时问，何时升级

新方向模糊时，分轮澄清谁在什么场景遇到什么问题、第一版要支持什么判断。每轮只问影响下一步的缺口，承接回答；不以建档为前提。场景和用途清楚即可开始；用户要先看一版，就说明可逆假设后推进。方向冲突或关键取舍再对齐。

| 模式 | 判断与动作 |
| -- | -- |
| 轻量日常迭代（默认） | 既有方向内实现、试用或普通接续。有实质需求变化，原位更新当前规则；入口只在状态或指针变动时更新。 |
| 项目基线变化 | 改变已确认的目标、边界、关键定义、承诺或验收依据：在权威源记下新决定、原因和影响范围。 |
| 里程碑收口 | 用户明确要求正式定稿、冻结、发布、阶段验收、移交或结束：只检查本次交付条件、证据、指针与未决项。 |

风险决定检查深度，不决定模式。耗时、迭代次数、“总结一下”“下次继续”都不是升级理由。普通暂停只留有用的恢复点。

## 跨会话留什么

- 沿用仍有效的上下文。新会话只看已有入口和任务相关材料；缺失、冲突或依赖变化才扩读。已有文档或 Issue 能接续就不另建骨架。
- 区分用户提出/确认的规则、AI 暂定选择和实际验证。更新当前有效逻辑，不把旧要求并列为现行，也不把实现当作用户认可。
- 一份正文一处维护。分清谁维护、约定对谁生效、谁实际采用了哪一部分；局部引用不等于全项目采用。
- 用熟悉的业务名让人找到当前工作成果、上次正式交付及其依据；不为导航复制正文或重排旧目录。活文档原位更新，需要独立交付快照才冻结。不同报告不是彼此的新版本。

## 验证到位，交还说重点

按用途、实际依赖和风险检查受影响的行为、交互、规则或计算，遵守项目必需检查。已有证据仍覆盖当前内容、输入和环境就复用；证据失效、检查失败或有实质疑点才补查。不因总结或交接重跑，不将 Demo 默认按生产系统全量回归。

交还时说清改了什么、现在按什么逻辑工作。只说明影响结论的验证边界；需要用户实测时，给具体操作和预期，区分 AI 自检与业务验收。不列无关的未测项，不凑固定栏目。

## 沿用明确授权

同一目标、对象和范围内，不因换轮次或到发送步骤再问；已授权发给指定对象即可发，“完成任务”不等于要通知别人。新增对象、范围外写入、敏感外发、显著费用、不可逆影响或关键方向不明时，只确认变化部分。遵守环境权限；重试前若结果不明，先查是否已生效。

## 可选工具

- [init_project.py](scripts/init_project.py)：确需新建时生成最小骨架；默认不写 AGENTS/CLAUDE。接管已有项目先只读盘点。
- [health_check.py](scripts/health_check.py)：核对指定入口的本地冻结指针，不证明业务正确或外链可访问。
- [check_terms.py](scripts/check_terms.py)：术语变化时核对受影响文件，不作为例行检查。
