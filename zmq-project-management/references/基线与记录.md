# 基线与记录

在项目基线变化、需要建立权威源、出现关键决策或准备交接时读取本文件。

## 项目基线

项目基线是后续工作默认遵循的已确认约定，包括：

- 目标、受众与用途。
- 范围、优先级与顺延项。
- 事实、术语、指标、规则和其他定义。
- 方法、路线、结构与关键依赖。
- 外部数据、许可、资源、预算和资格条件。
- 风险、授权边界与不可触碰项。
- 验收标准。
- 已确认的关键决策。

普通实现细节、临时尝试和可在既有基线内自由选择的方法，不自动成为项目基线。

## 唯一权威源

同一类定义只选择一个权威源。名称按项目语境决定，例如：

| 项目语境 | 可能的权威源 |
| -- | -- |
| 分析与研究 | 口径字典、样本与方法说明、证据规则 |
| 开发与流程 | 契约清单、需求基线、规则清单 |
| 设计与内容 | 设计原则、术语与事实、风格与红线 |
| 运营与活动 | 活动规则、名单口径、预算边界 |
| 通用项目 | 基线说明、约束清单 |

不要为了统一命名强迫所有项目使用“契约”或“产品口径”。

更新权威源时：

1. 原位修改活文档。
2. 记录旧定义、新定义、原因和影响范围。
3. 只同步真正引用该定义的当前材料。
4. 不在 README、计划、台账和验收材料中重复完整定义；只记录指针或变化摘要。

## 台账记录标准

只记录以下事件：

- 改变项目基线的关键决策。
- 有截止条件和默认方案的待确认事项。
- 会影响后续执行的风险或阻塞。
- 已采用方案被推翻或纠正。
- 正式里程碑结果。
- 多人或多 AI 需要知道的跨会话交接结果。
- 用户明确要求留痕的事项。

普通进展、已由版本控制清楚表达的文件修改、重复测试结果和闲聊不落账。

关键决策写法：

> 原来是什么 → 改成什么 → 为什么 → 影响什么。

使用 D-xxx 标识已决策，P-xxx 标识待确认。待确认项至少包含决策人、截止条件、默认方案和影响范围。

同一变化通常只写一条决策，不再拆成“推翻、进展、验收”三条重复记录。只有这些事件发生在不同时间、承担不同交接含义时才拆分。

## README 更新触发

README 仅保存当前状态，不承担历史流水。满足任一条件时更新：

- 阶段或正式状态变化。
- 下一步发生实质变化。
- 新增或解除阻塞。
- 当前冻结交付物或权威源指针变化。
- 项目长期挂起、恢复或交接。

普通任务完成但不改变上述内容时，不更新 README。

新会话恢复上下文时，先读 README 当前状态。只有任务依赖历史决策时，才在台账中按编号、关键词或相关阶段定向查找，不默认读取最近固定条数。

## 多执行者协作

- 共用一套 README、权威源和台账。
- 在关键事件中注明执行者。
- 执行前检查直接相关文件是否有并行修改。
- 发生冲突时以文件系统和版本控制状态为事实，先澄清再改记录。
- 不为每位执行者创建独立台账。
